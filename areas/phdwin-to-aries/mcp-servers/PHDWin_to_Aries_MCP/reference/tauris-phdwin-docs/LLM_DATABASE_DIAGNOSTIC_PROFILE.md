# LLM Database Diagnostic Profile

## Purpose

This document defines the lightweight markdown profile Tauris should generate for each ingested PHDWin or Aries database before deeper LLM analysis.

The goal is to give a local LLM a compact, factual orientation layer:

- what database was loaded
- what source files and companion documents were provided
- what projects, wells, cases, reserves, ownership, geography, and attributes exist
- where key values live in PHDWin and Aries structures
- what looks complete, missing, inconsistent, or worth a deeper review

This profile should be generated once per ingested database and stored with the import job artifacts. It should be short enough for retrieval/context injection but specific enough to guide follow-up questions.

## Recommended File Model

Use one generated markdown profile per database import:

```text
<job-id>/database-profile.md
```

Do not split PHDWin and Aries into separate generated files yet. Most diligence questions need a crosswalk between the seller/source database, normalized staging tables, Aries export tables, and supporting documents. A single profile keeps the LLM grounded in one source of truth.

If the profile becomes too large later, split into:

- `database-profile.md`: executive/context summary
- `phdwin-diagnostics.md`: source PHDWin details
- `aries-diagnostics.md`: resolved Aries/export details
- `document-profile.md`: PDF/report summary

## Reserve Category Summary

Use this section to orient the LLM before questions about PDP, PDNP, PUD, proved/probable/possible, reserve class, reserve category, or seller category language.

Do not assume every database uses the same exact reserve labels. Capture both the standard Tauris interpretation and the literal database values.

PHDWin reserve category/class data is generally more standardized through source tables such as `PHD_CATEGORY`, `PHD_CLASS`, `PHD_IDLABELS`, and `PHD_IDCODES`.

Aries reserve category data is often less standardized. Different databases may abbreviate the same idea differently, and many databases carry multiple time-stamped or vintage-specific reserve category fields such as `RSV_CAT`, `RSV_CAT24`, `YE_RESCAT`, or other seller-defined qualifier fields. For Aries, the project sort/filter definitions are the governing context: inspect `PROJECT`, `PROJLIST`, `SelFilters`, and `SORTFILTERS` to determine which qualifier fields are actually used for each project.

### PHDWin Questions For The LLM

- What are the main project/group definitions?
- What effective/as-of date should be used for each project or database summary?
- Which fields appear to define reserves category, class, status, or evaluation scope?
- Do PHDWin reserve category/class lookup tables provide a clear standardized mapping?
- Which attributes indicate geography or asset location?
- Which attributes indicate legal/unit ownership or DSU information?
- Is lateral length present directly, by ID code, or only in companion documents?
- How many owners/partners exist, and are owner rows complete by well/case?
- Are there filters that exclude wells from seller economics?
- Are groups being used as incrementals or simple reporting groups?

### Aries Questions For The LLM

- Does `AC_PROPERTY` contain enough property identity and location data to support retrieval?
- Are reserve categories explicitly populated or only inferable from project filters?
- Do `PROJECT` and `PROJLIST` describe the same project universe as the PHDWin source?
- Are `SelFilters` and `SORTFILTERS` preserving seller/provider grouping logic?
- Which abbreviated Aries fields look like reserve category qualifiers, such as `RSV_CAT`, `RSV_CAT24`, `YE_RESCAT`, or seller-specific variants?
- Which reserve qualifier fields are actually referenced by each Aries project's sort and filter rows?
- What scenarios exist, and which projects/properties do they apply to?
- What qualifiers exist, and do they change inclusion, reserves category, ownership, or economics?
- Are economic outputs populated enough for a useful database-level summary?
- Are missing values conversion gaps or genuinely absent source data?

## Implementation Notes

The generated profile should be built from staged PostgreSQL data after extraction and diagnostics refresh. Do not query the Clarion driver for profile generation once staging is complete.

Recommended first implementation:

1. Generate row counts from staged `job_*` tables.
2. Generate project/case counts from `PHD_TITLES`, `PHD_MAINLSE`, and, when available, Aries `PROJECT`/`PROJLIST`.
3. Generate effective/as-of date coverage from `PHD_TITLES`, project/scenario tables, Aries setup tables, and companion reports.
4. Generate PHDWin owner diagnostics from `PHD_OWNER`, `PHD_ADJOWNER`, and `PHD_MAINLSE`.
5. Generate Aries scenario diagnostics from Aries scenario/setup tables and, for converted PHDWin datasets, `MOD_SCEN`.
6. Generate Aries qualifier diagnostics from `AC_PROPERTY`, `PROJECT`, `PROJLIST`, `SelFilters`, `SORTFILTERS`, setup/default tables, and any qualifier-like columns or attributes.
7. Generate PHDWin reserve category coverage from `PHD_CATEGORY`, `PHD_CLASS`, `PHD_IDCODES`, and `PHD_IDLABELS`.
8. Generate Aries reserve category coverage by:
   - scanning `AC_PROPERTY` and other Aries tables for qualifier-like field names
   - scanning for field names containing or resembling reserve/category abbreviations such as `rsv`, `res`, `cat`, `class`, `reserve`, `ye`, and year/vintage suffixes
   - recording literal field names such as `RSV_CAT`, `RSV_CAT24`, and `YE_RESCAT`
   - inspecting `PROJECT`, `PROJLIST`, `SelFilters`, and `SORTFILTERS` to identify which qualifier fields govern each project
   - treating project sort/filter usage as the governing interpretation for Aries project-level reserve summaries
9. Generate spatial/legal/attribute coverage by scanning ID labels/codes and known Aries property columns for names such as:
   - state
   - county
   - parish
   - basin
   - field
   - reservoir
   - formation
   - operator
   - API
   - unit
   - DSU
   - tract
   - lease
   - lateral
   - length
   - effective
   - asof
   - as_of
   - scenario
   - qualifier
10. Attach companion document summaries as separate evidence, clearly labeled as seller/provider perspective.
11. Keep generated statements factual and cite source tables/fields for every business conclusion.
